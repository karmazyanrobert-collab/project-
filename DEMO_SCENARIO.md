# DEMO SCENARIO — сценарий демонстрации преподавателю

## 1. Короткое вступление

Скажи:

> Это демонстрационная университетская Data Platform без Docker. Она показывает полный цикл: генерация данных, lakehouse-слои Bronze/Silver/Gold, проверки качества данных, feature store, streaming и аналитический dashboard.

Покажи, что главный файл приложения:

```bash
streamlit run dashboard/app.py
```

Если warehouse ещё не создан, dashboard сам запускает pipeline и создаёт `data/warehouse.duckdb`.

## 2. Что показать сначала

1. Открой dashboard.
2. Покажи верхние KPI:
   - количество студентов;
   - средний балл;
   - студентов в зоне риска;
   - долю риска;
   - средний completion rate.
3. Объясни, что это не статичная картинка: метрики читаются из DuckDB warehouse, который был собран pipeline.

## 3. Как объяснить Bronze / Silver / Gold

### Bronze

Bronze — это сырой слой данных.

Что сказать:

> В Bronze мы сохраняем исходные данные максимально близко к источнику. Здесь данные ещё могут содержать ошибки: дубли, пропуски, некорректные оценки.

Пример источников:

- студенты;
- курсы;
- оценки;
- задания;
- LMS-активность;
- аудитории;
- события входа/выхода из аудиторий.

### Silver

Silver — очищенный слой.

Что сказать:

> В Silver удаляются или исправляются технические проблемы: дубли student_id, пустые имена, оценки вне диапазона 0–100. Этот слой уже можно безопасно использовать для аналитики.

### Gold

Gold — бизнес-витрины.

Что сказать:

> В Gold данные агрегируются в понятные аналитические таблицы: успеваемость студентов, показатели факультетов, LMS engagement и загрузка аудиторий. Dashboard работает именно с этим слоем через DuckDB.

## 4. Как объяснить Data Quality

Покажи лог pipeline или файл `logs/data_quality_report.csv` после запуска pipeline.

Что сказать:

> Data Quality checks запускаются два раза: сначала на Bronze, потом на Silver. На Bronze специально могут быть ошибки, чтобы показать работу контроля качества. На Silver проверки должны пройти успешно после очистки данных.

Примеры проверок:

- `student_id` не должен быть пустым;
- `student_id` должен быть уникальным;
- `grade` должен быть от 0 до 100;
- `submitted` должен быть boolean;
- `capacity` аудитории должна быть больше 0.

Главная идея:

> Data Quality нужен, чтобы не пускать грязные данные в аналитический слой и dashboard.

## 5. Как объяснить Feature Store

В dashboard открой блок **Feature Store Preview**.

Что сказать:

> Feature Store — это набор подготовленных признаков для ML или риск-скоринга. Вместо того чтобы каждый раз пересчитывать признаки из сырых таблиц, pipeline заранее формирует student_features.parquet.

Примеры признаков:

- средний балл студента;
- completion rate;
- количество LMS-событий;
- engagement score;
- risk flag.

Как объяснить пользу:

> Эти признаки можно использовать для модели, которая предсказывает академический риск или рекомендует студентам поддержку.

## 6. Как объяснить Streaming

Если есть время, запусти в отдельном терминале:

```bash
python run_streaming_demo.py
```

Что сказать:

> Здесь Kafka заменена простым файловым stream. Producer пишет события в JSONL-файл, consumer читает новые события и обновляет streaming-таблицы в DuckDB.

Покажи в dashboard блок **Streaming Analytics**.

Объясни метрики:

- Events / Minute — поток событий в минуту;
- Active Students — активные студенты за последние 5 минут;
- Assignment Submissions — отправки заданий за окно времени;
- Building Entries — входы в здания.

Главная идея:

> Даже без Kafka можно показать архитектурный принцип streaming: события поступают постоянно, consumer обновляет таблицы, dashboard показывает свежие показатели.

## 7. Как объяснить Dashboard

Покажи основные блоки:

1. **KPI cards** — быстрый обзор состояния университета.
2. **Faculty Analytics** — сравнение факультетов.
3. **Drill-down** — переход от факультета к группе и студентам.
4. **LMS Engagement** — активность студентов в LMS.
5. **Room Utilization** — загрузка аудиторий.
6. **Feature Store Preview** — ML-признаки.
7. **Streaming Analytics** — потоковые метрики.

Что сказать:

> Dashboard — это финальная точка платформы. Он не хранит бизнес-логику внутри себя, а обращается к semantic layer и DuckDB warehouse.

## 8. Финальное резюме для защиты

Можно завершить так:

> Проект показывает end-to-end Data Platform: источники → Bronze → Data Quality → Silver → Gold → Feature Store → DuckDB Warehouse → Semantic Layer → Dashboard → Streaming. Он готов к облачному запуску в GitHub Codespaces и Streamlit Community Cloud без Docker, Windows-настроек и ручной загрузки данных.
